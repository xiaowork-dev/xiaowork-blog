## 2. 实际完成内容

1. **修复**（`deploy/lib.sh` 新增 `fetch_release_tags`，`manage.sh` 与 `update.sh` 共用）：
   - 先执行 `git fetch --tags`；
   - 遇到 “would clobber existing tag” 时，逐个比较本地标签与远端标签解引用后的提交：
     - **相同**：用远端标签替换本地标签（只强制更新这一个标签），然后继续；
     - **不同**：判定为发布标签被移动，拒绝并返回 2，同时显示本地与远端的提交；
   - 网络错误返回 1，并附带错误信息。
   - 两个调用方的提示：
     - `manage.sh`：“远端发布标签指向的提交与本地不同：v0.2.0(本地 … / 远端 …)…”；
     - `update.sh`：“发布标签不允许移动…网站仍在运行当前版本”。
   - 部署时记录的标签 → 提交（`state/tags`），仍作为第二层检查保留。
2. **CI**（`deploy` 作业）：
   - `actions/checkout` 改为 `fetch-depth: 0`，拉取完整历史与注释标签，与服务器上 `git clone` 的结果一致；
   - 新增回归测试步骤：取远端第一个 `v*` 标签，在本地改成同一提交的轻量标签，要求被替换为注释标签；再改到父提交，要求返回 2；最后恢复。
3. **文档**：
   - `docs/releases/v1.0.0-rc.2.md`；
   - `CHANGELOG.md` 的 `[1.0.0-rc.2]`；
   - README 当前状态；
   - 上线检查清单中的版本号改为 rc.2，原“验收中修复则发布 rc.2”的预案顺延为 rc.3。
4. **发布**：
   - 在 `b81de95` 上创建带注释的标签 `v1.0.0-rc.2`（标签对象 `dfa63249b799618b03f99f261d8aac2030125483`），用普通推送推到远端；
   - 用项目负责人已登录的 Chrome，在网页上创建 Release：选择已存在的标签，勾选 Pre-release，说明使用目标提交中的 `docs/releases/v1.0.0-rc.2.md`。
   - 地址：https://github.com/xiaowork-dev/xiaowork-blog/releases/tag/v1.0.0-rc.2
   - rc.1 的 Release 保持不变（不可变，内容没有问题）。rc.2 的说明中注明取代 rc.1，并给出从 rc.1 升级的命令。

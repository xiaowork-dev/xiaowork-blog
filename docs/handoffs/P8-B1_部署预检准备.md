## 4. 只读服务器预检

### 4.1 推荐方式：一次性执行只读脚本，不在服务器上留下文件

授权后，我会在本机执行（脚本经 SSH 标准输入传过去，服务器上不需要先克隆仓库）：

```bash
ssh xwb-prod 'sudo bash -s -- --npm-network <NPM 网络名> --data-dir /srv/xiaowork-blog --domain <域名> --smtp <SMTP 主机>:587' < deploy/precheck.sh
```

`deploy/precheck.sh` 的约束：

- 只执行读取类命令：不创建文件、目录、容器、网络或数据卷，不拉取镜像，不进入任何容器；
- 不输出容器环境变量、完整的 `docker inspect` 或任何 `.env` 内容，避免泄露其他业务的密钥；
- 只向 GitHub、Go 与 npm 源、Docker Hub 发起只读 HTTP 请求，并对 SMTP 端口做一次 TCP 连接测试（不登录、不发信）。

### 4.2 脚本中的检查项与用途

| 节 | 命令（摘要） | 用途 |
|---|---|---|
| 1 系统 | `/etc/os-release`、`uname -srm`、`timedatectl`、`uptime` | 系统、架构、时间同步（令牌有效期与证书依赖准确时间） |
| 2 资源 | `nproc`、`free -m`、`df -hP / /var/lib/docker <DATA_DIR 上级>`、`df -iP /` | 构建所需内存，镜像与数据所需磁盘、inode |
| 3 Docker | `docker version`、`docker compose version`、`docker info -f …`、`daemon.json` 中的网络相关键 | 版本要求（Engine 24+、Compose 2.20+），rootless、`userland-proxy`、`iptables`、地址池等会影响真实 IP 与网段的设置 |
| 4 容器 | `docker ps -a --format 名称/镜像/状态/端口` | 现有业务；确认没有同名容器 |
| 5 端口 | `ss -Htlnp` | 80/443/81 由谁占用（NPM 还是 1Panel 的 OpenResty） |
| 6 网络 | `docker network ls`、`docker network inspect -f 名称/驱动/网段`、`ip -4 route` | 自动判断 `APP_SUBNET` 是否与现有 Docker 网络或主机路由重叠 |
| 7 NPM | 按镜像名找到 NPM 容器，`docker inspect -f` 只取网络、IP、端口、挂载、重启策略、compose 标签；`--npm-network` 时列出该网络的驱动、网段与成员 | 确定 `PROXY_NETWORK`；判断 NPM 是否只在默认 bridge 上（需要方案 B） |
| 8 面板 | `systemctl list-units`、容器名、`/opt/1panel` | 1Panel、OpenResty、宝塔等是否在运行 |
| 9 已有资源 | 以 `xiaowork-blog` 开头的容器、卷、镜像、网络；`/opt/xiaowork-blog`、`DATA_DIR` 是否存在 | 应该全部为空；不为空时先停下确认来源 |
| 10 防火墙 | `ufw status`、`firewall-cmd --state`、nftables 规则数 | 记录现状（本项目不新增端口） |
| 11 外部连通性 | `curl` GitHub、proxy.golang.org、goproxy.cn、npm 两个源、Docker Hub；SMTP TCP；`getent ahosts 域名`、本机地址 | 构建能否下载依赖、是否需要镜像源；SMTP 端口是否被封；DNS 是否指向本机 |
| 12 工具 | git、openssl、sha256sum、bash、curl、crontab、rsync | 部署脚本与备份所需工具 |

### 4.3 补充的人工只读检查（按需）

```bash
ssh xwb-prod 'docker network inspect <NPM 网络名> -f "{{range .Containers}}{{.Name}} {{end}}"'   # 该网络上还有哪些业务（决定是否收紧可信代理）

```

## 5. 与现有 Nginx Proxy Manager 的集成方案

### 5.1 原则

- NPM 继续独立运行。博客**不占用** 80/443，不发布任何端口，也不修改 NPM 的容器、镜像、数据卷或已有代理主机。
- 唯一需要在 NPM 中做的改动是**新增一个 Proxy Host**，在 NPM 界面中操作（由您登录，或在您授权并亲自登录后由我操作界面）。
- 博客的 api / web 加入 NPM 所在的 Docker 网络，NPM 通过容器别名访问它们。

### 5.2 网络方案（由预检第 7 节决定）

| 方案 | 适用情况 | 做法 | 对 NPM 的影响 |
|---|---|---|---|
| **A（首选）** | NPM 在一个**自定义网络**上（例如 `npm_default`、`1panel-network`） | `.env` 中 `PROXY_NETWORK=<该网络>`；`install.sh` 让博客的 api / web 加入该网络 | **无**：NPM 不重启、不改配置 |
| B | NPM 只连接在默认 `bridge` 网络上（没有容器名解析）；或者该网络上有很多不相关的业务、希望隔离 | 新建专用网络 `docker network create xiaowork-proxy`，执行 `docker network connect xiaowork-proxy <NPM 容器>` 把 NPM 加入，`PROXY_NETWORK=xiaowork-proxy` | `network connect` 不会重启 NPM，但**改变了 NPM 的网络**，需要单独授权。<br>NPM 被重建（例如升级）后这条连接会丢失，需要同时写入 NPM 的 compose 文件或 1Panel 应用配置，否则博客会 502 |
| 不采用 | — | 把 api / web 发布到主机端口，让 NPM 转发到主机 IP | 违反“应用端口不对外暴露”的要求，不采用 |

`lib.sh` 已拒绝 `PROXY_NETWORK=bridge|host|none`，并在网络中没有其他容器时发出警告。

### 5.3 Proxy Host 设置（与运维手册 §4 一致）

| 位置 | 设置 |
|---|---|
| Details | 域名；`http` → `xiaowork-blog-web`:`3000`；勾选 Block Common Exploits |
| Custom locations | `/api/v1/` 与 `/media/` → `http` `xiaowork-blog-api`:`8080` |
| SSL | Let's Encrypt；Force SSL；HTTP/2 |
| Advanced | `client_max_body_size 12m;` |

### 5.4 可信代理

- 方案 A 中，`install.sh` 默认信任整个 NPM 网络网段加上 `APP_SUBNET`。如果预检显示该网络上还有其他业务容器，建议改为只信任 NPM 的 `/32` 加 `APP_SUBNET`（需要 NPM 有固定 IP，方法见运维手册 §12）。
- 方案 B 的专用网络中只有 NPM 和博客，整个网段都可以信任。
- 经过 CDN 时，要先在 NPM 中配置 CDN 的真实 IP（`real_ip_header` 与 CDN 的 IP 段），否则所有访客共享 CDN 出口 IP 的限流额度。

## 7. 风险与防误操作措施

| # | 风险 | 措施 |
|---|---|---|
| K1 | 误操作影响服务器上的其他业务 | - 所有命令固定 `-p xiaowork-blog`；<br>- 容器、卷、网络、镜像都以 `xiaowork-blog` 为前缀；<br>- 部署前预检确认没有同名资源；<br>- **禁止** `docker system prune`、`docker volume prune`、`docker network prune`、`docker compose down -v`、`docker rm` 他人容器；<br>- 脚本中没有这些命令 |
| K2 | 80/443 冲突（1Panel 的 OpenResty 与 NPM） | 博客不占用端口；预检确认 80/443 的占用者。如果 OpenResty 正在占用，**停止并请您决定**，不由部署方自行调整 |
| K3 | 修改 NPM | 只新增一个 Proxy Host；方案 B 的 `network connect` 需要单独授权，并同步写入 NPM 的持久化配置 |
| K4 | 网段冲突导致网络创建失败 | 预检自动判断；compose 在冲突时直接报错退出，不会影响现有网络 |
| K5 | 服务器内存不足导致构建失败 | 预检检查内存与 swap；构建失败时不会切换版本；必要时由您决定是否增加 swap |
| K6 | 经过 CDN 或 rootless Docker 时拿不到真实客户端 IP | 预检第 3 节与 DNS 检查；上线后用手机网络验证（上线检查清单 C5） |
| K7 | 密钥泄露 | - `.env` 在服务器上生成，权限 600；<br>- SMTP 密码由您在服务器上填写；<br>- 预检不输出环境变量；<br>- 聊天和 GitHub 中不出现任何密钥；<br>- 备份目录权限 700 |
| K8 | 恢复脚本覆盖数据 | `restore.sh` 需要输入 RESTORE，先做安全备份，原图片目录改名保留。**生产首次部署不会执行恢复** |
| K9 | 首次部署后才发现问题 | 回退方法：在 NPM 中停用该 Proxy Host（不影响其他站点）；博客容器可以 `docker compose -p xiaowork-blog stop`，数据保留 |
| K10 | 执行偏离计划 | - 每一步先列出命令再执行；<br>- 输出与预期不符（例如出现同名资源、端口被意外占用、磁盘不足）时**立即停止并汇报**，不做临时修补 |
| K11 | 中国大陆网络 | 预检确认可达性，按需设置 `GOPROXY=https://goproxy.cn,direct` 与 `NPM_REGISTRY=https://registry.npmmirror.com/` |

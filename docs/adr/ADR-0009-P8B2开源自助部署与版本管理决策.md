# ADR-0009 — P8-B2 开源自助部署与版本管理

- 日期：2026-10-24
- 状态：已采纳（P8-B2）
- 依据：项目负责人的 P8-B2 要求（开源发布、用户自助部署、GitHub Releases 版本管理、不自动部署）；ADR-0008

**没有数据库迁移（仍为版本 7）**。本阶段没有连接任何服务器，也没有创建 GitHub Release。

| # | 决定 | 理由 |
|---|---|---|
| 1 | **统一入口 `deploy/manage.sh`**：install、status、check、update、rollback、backup、restore、precheck、admin，以及不带参数时的交互菜单。<br>更新、回滚、备份、恢复仍由已有的 `update.sh`、`rollback.sh` 等执行，`manage.sh` 只负责选择版本、展示计划和确认 | 复用 P8-A 已验证的备份、迁移、自动回滚逻辑，不重复实现 |
| 2 | **版本来源是 GitHub Releases**，只认标签为 `vX.Y.Z[-后缀]` 的已发布 Release，忽略草稿。<br>- 带后缀或标为 pre-release 的是**预发布版**，只有加 `--pre` 才显示和选用；<br>- 其余为**正式版**，默认推荐其中最新的一个（按语义化版本排序）；<br>- 分支和未发布的提交是**开发代码**，只作为信息显示，必须加 `--allow-unreleased` 才能安装 | “只推荐正式稳定版本，不能默认安装未发布的 main 代码” |
| 3 | `update.sh` **不再有默认目标**（以前默认 `origin/main`）：必须 `--ref` 或 `--no-fetch`。分支名会解析为 `origin/<分支>` 并警告“开发代码” | 防止误把 `main` 部署到生产 |
| 4 | **标签不可变的检查**：<br>- 每次部署后，在 `DATA_DIR/state/tags` 记录“标签 → 提交”，之后同名标签指向别的提交时拒绝继续；<br>- `git fetch` 不强制更新已有标签，远端移动标签时 fetch 失败，脚本把它报告为“标签被改动”；<br>- 维护者侧：标签规则集禁止更新 / 删除 `v*`，并开启 Release immutability（`docs/RELEASING.md` §3） | 正式版本必须对应不可变的标签和提交 |
| 5 | **更新前展示计划并确认**：<br>- 当前与目标的版本、提交、发布日期；<br>- 升级、降级还是切换提交线（`git merge-base --is-ancestor`）；<br>- `git diff --name-status` 得到的迁移变化：新增的迁移、降级后目标版本不认识的迁移，以及被修改的历史迁移；<br>- 更新说明前 25 行。<br>终端中需要输入目标版本号确认；非终端必须加 `--yes`，否则拒绝 | 用户主动选择并确认；明确数据库结构不会自动回退 |
| 6 | **GitHub 不可用时不影响网站**：<br>- 连接失败、HTTP 403 / 429（速率限制）、404、其他状态码、响应不是 JSON 都在**任何改动之前**报错退出；<br>- 可选 `GITHUB_TOKEN` 只用于提高匿名速率限制 | 检查失败时网站继续运行当前版本 |
| 7 | **用 Node 解析 JSON**：在 web 构建本来就需要的固定镜像 `node:24.22.1-alpine`（版本从 `apps/web/Dockerfile` 读取）中运行，加 `--network none` | 服务器不必安装 jq 或 Python；不新增依赖 |
| 8 | **首次安装引导**：<br>- `install.sh` 生成 `.env`（随机密码与密钥）后，在终端中逐项询问域名、数据目录、NPM 网络（列出现有自定义网络与成员）、内部网段（自动推荐不冲突的网段）和 SMTP（密码不回显）；<br>- 写入时值加单引号，单引号本身被拒绝；<br>- 非终端时保持原行为：生成文件后退出，由用户编辑 | 降低新用户的配置门槛；docker compose 会展开未加引号的 `$` |
| 9 | **安装前冲突检查**：内部网段与现有 Docker 网络是否重叠（重叠时拒绝）；443 无监听时警告（NPM 可能未运行）；`PROXY_NETWORK` 不能是预置网络（P8-B1）。<br>完整的只读报告仍是 `precheck.sh`，可通过 `manage.sh precheck` 运行，并自动带上 `.env` 中的参数 | 端口与网段冲突要在启动前发现 |
| 10 | **不提供 `curl \| bash` 安装**、不提供自动更新（无 cron、无 webhook、无 GitHub Actions 部署） | 用户可以先审查脚本；生产网站只由所有者主动更新 |
| 11 | **继续依赖 Nginx Proxy Manager**。独立反向代理模式（例如内置 Caddy 自动申请证书）列为后续候选，需要单独评审 | 不扩大本次范围 |
| 12 | **首个正式版本的上线顺序**：先发布预发布版 `v1.0.0-rc.1`，生产环境用 `--pre` 安装并验收；通过后在同一提交上发布 `v1.0.0`，服务器无需重新部署 | 正式版本必须在上线验收之后发布，而 `manage.sh` 只安装已发布的版本 |
| 13 | **README 面向部署者**：开发相关的内容移到 `docs/开发指南.md`；新增 `CHANGELOG.md`、`CONTRIBUTING.md`、`SECURITY.md`、`docs/RELEASING.md` 和 `docs/开源许可审查.md` | 开源用户首先需要知道怎么安装和更新 |
| 14 | **许可证暂不确定**：审查结论推荐 MIT，但由项目负责人确认版权主体和协议后再加入 `LICENSE` | 用户要求 |

## 后果

- 在发布第一个 Release 之前，`manage.sh install` 会报告“还没有正式发布的版本”；测试只能显式使用 `--allow-unreleased main`。
- 分叉仓库（fork）没有原仓库的 Release。分叉的用户需要自己发布 Release，或设置 `GITHUB_REPO=原仓库`；后者会安装原仓库的标签，而这些标签必须在自己的 origin 中存在。
- 匿名 GitHub API 每小时 60 次，对于手动检查足够。

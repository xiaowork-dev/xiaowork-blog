# ADR-0008 — P8-A 上线准备：隐私加固、生产部署、更新回滚与备份恢复

- 日期：2026-10-24
- 状态：已采纳（P8-A）；生产部署（P8-B）另行授权
- 依据：PRD MEDIA-07、§4、§6 非功能需求、UAT；SAD §2、§5 部署视图；API-DD §2、§7；DD §9；实施计划 P8

**没有数据库迁移（仍为版本 7）**。P8-A 不连接生产 VPS、不配置正式域名、不使用正式 SMTP 密钥、不触碰现有 Nginx Proxy Manager（NPM）。

| # | 决定 | 依据 / 理由 |
|---|---|---|
| 1 | **上传图片去除隐私元数据（P7 记录的 EXIF 风险）**：<br>- 在校验格式与尺寸之后、计算 SHA-256 之前，**无损**改写临时文件：<br>&nbsp;&nbsp;JPEG 删除 APP1（EXIF/XMP）、APP3–APP13、APP15、COM，保留 APP0（JFIF）、APP2（ICC 色彩）、APP14（Adobe）；<br>&nbsp;&nbsp;PNG 删除 tEXt / zTXt / iTXt / eXIf / tIME；<br>&nbsp;&nbsp;WebP 删除 EXIF、XMP 块并修正 VP8X 标志与 RIFF 长度；<br>&nbsp;&nbsp;GIF 删除注释扩展和非循环用途的应用扩展；<br>- JPEG 的方向（Orientation ≠ 1）改写为一个只含方向的最小 EXIF 块，显示方向不变；缩略图按方向旋转；<br>- 改写后重新 `DecodeConfig` 校验格式与尺寸一致，`size_bytes`、`sha256` 按改写后的文件记录；<br>- 头像与文章 / 站点图片走同一流程；上传界面提示“会自动移除 EXIF/GPS 等隐私信息”。<br>**像素不重新编码**，因此画质、色彩与动图都不受影响 | PRD MEDIA-07；隐私最小化。<br>重新编码会损失画质且改变动图，无损剥离已足够去除 GPS、设备、作者等信息 |
| 2 | 已经存储的图片**不批量回溯处理**：本地开发数据只有测试图片，生产环境尚无数据 | 避免改写已被引用文件的 sha256 |
| 3 | **Web 安全响应头**（Nitro `render:response` 插件 `server/plugins/security-headers.ts`）：<br>- 删除 `X-Powered-By`；<br>- `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`（认证页保留 `no-referrer`）、`Permissions-Policy`；<br>- CSP：`default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`；<br>- 只有 `public.siteUrl` 为 https 时才发送 HSTS（一年，不含 includeSubDomains / preload）。<br>`'unsafe-inline'` 是 Nuxt SSR 内联数据与防闪烁主题脚本所需；XSS 的主防线仍是 Markdown 渲染器关闭原始 HTML 与地址白名单（P4/P5） | SAD 安全设计；浏览器实测编辑器、Shiki、预览、评论与 12 个页面均无 CSP 违规 |
| 4 | **生产 Compose**（`deploy/compose.prod.yaml`）：<br>- 任何服务都**不发布主机端口**；NPM 经共享网络访问 `xiaowork-blog-web:3000` 与 `xiaowork-blog-api:8080`；<br>- 数据库只在 `internal: true` 的 `backend` 网络上；<br>- api / web 只读根文件系统、`tmpfs /tmp`、`cap_drop: ALL`、`no-new-privileges`；日志限制为 10 MB × 5；<br>- 数据卷固定命名 `xiaowork-blog_pgdata`，图片目录为主机 `DATA_DIR/media`；<br>- PostgreSQL 使用 `log_error_verbosity=terse`，避免唯一约束错误把邮箱写入日志 | SAD 部署视图；P8-A 日志审查发现 |
| 5 | **镜像在服务器上从当前提交构建**，标签为 12 位提交 SHA；保留当前与上一版本镜像用于回滚，不引入镜像仓库 | 单机部署，少一个服务；回滚不依赖网络 |
| 6 | **可信代理**：`TRUSTED_PROXY_CIDRS` 留空时，`install.sh` 自动写入 NPM 网络网段与固定的 `APP_SUBNET`（Nuxt SSR → API）。<br>只有直接对端可信时才读取 `X-Forwarded-For`，并从右向左跳过可信跳。<br>演练中从网络外部伪造的 `X-Forwarded-For` 被忽略（API 使用真实对端地址） | P2 ClientIP；限流与审计需要真实 IP |
| 7 | **一键脚本**（`deploy/*.sh`，均可重复执行）：<br>- `install.sh`：首次生成 `.env`（随机数据库密码与 APP_SECRET_KEY）；再次运行完成检查、构建、迁移、启动、健康检查与冒烟测试；已正常运行时直接退出；<br>- `update.sh`：拒绝脏工作区 → 构建新镜像（旧版本继续服务）→ 完整备份 → 应用 db 服务变更 → 用新镜像迁移（失败则停在旧版本）→ 切换 api/web → 健康检查与冒烟测试 → 失败自动切回旧镜像；<br>- `rollback.sh`：切回上一版本镜像；<br>- `backup.sh` / `restore.sh`：见第 8 条；<br>- `admin.sh`：创建首个管理员、媒体一致性检查、状态。<br>**迁移只向前、不自动回退**：迁移遵循“只增不删”，旧代码可在新结构上运行；需要旧结构时用更新前备份恢复 | 用户要求一键部署与更新；不得删除持久化数据 |
| 8 | **备份**：`pg_dump -Fc` + `media.tar.gz` + `env.backup` + `manifest.txt` + `SHA256SUMS`，目录 `DATA_DIR/backups/<UTC 时间>-<标签>`，保留最近 `BACKUP_KEEP` 份（默认 14）。<br>**恢复**：校验 → 安全备份当前状态 → 停 api/web → 重建数据库并 `pg_restore --exit-on-error` → 当前图片目录**改名保留**后解包 → 迁移 → 启动 → 健康检查。<br>异地备份用 rsync/rclone 同步 `DATA_DIR/backups`，目标在 P8-B 确定 | 用户要求；恢复不删除任何现有数据 |
| 9 | `deploy/.env` 按 docker compose 的 dotenv 语法**逐行解析**，不用 shell `source`（`SMTP_FROM=名称 <地址>` 在 shell 中是重定向） | 演练中发现 |
| 10 | Nitro `compressPublicAssets`（gzip + brotli）：`/_nuxt` 静态资源预压缩，不依赖反向代理开启压缩 | 性能基线：首页首屏 JS 从 241 KiB（未压缩）降低 |
| 11 | **隔离演练环境**（`deploy/test/drill.sh`）：Docker-in-Docker 容器扮演全新 Linux 服务器；nginx 容器按 `deploy/nginx/npm-equivalent.conf` 模拟 NPM（自签名 HTTPS），Mailpit 模拟 SMTP；裸 Git 仓库扮演 GitHub。<br>开发机的 Docker 卷与数据不受影响 | 用户要求在隔离 Linux 环境验证 Linux 特有行为 |

## 后果

- 新上传的照片不再携带位置、设备与作者信息；此前上传的本地测试图片不受影响。
- `update.sh` 会在每次更新前做一次完整备份，磁盘需要预留空间（脚本检查 3 GB）。
- 回滚只切换应用镜像，不回退数据库结构；需要回到更新前的数据时必须使用 `restore.sh`，这会丢失更新之后产生的数据。
- 可信网段包含整个 NPM 网络：同一网络上的其他容器可以伪造 `X-Forwarded-For`。如需收紧，可给 NPM 固定 IP 并把 `TRUSTED_PROXY_CIDRS` 改为该地址 `/32` 加 `APP_SUBNET`（见运维手册）。

# ADR-0010 — P8-B6 反代方式：支持 1Panel OpenResty 主机网络部署

- 日期：2026-10-25
- 状态：已采纳（P8-B6，等待项目负责人验收）
- 依据：项目负责人的 P8-B6 要求（目标 VPS 上 1Panel 的 OpenResty 使用主机网络并占用 80/443，不在任何 Docker 自定义网络中）；ADR-0008、ADR-0009 第 11 条

**没有数据库迁移（仍为版本 7）**。本阶段没有连接任何服务器，没有修改 1Panel、OpenResty 或 ERP 服务，也没有创建标签或 Release。

| # | 决定 | 理由 |
|---|---|---|
| 1 | 新增 **`PROXY_MODE`**，取值如下：<br>- `docker-network`（默认）：NPM 等容器反代，共享 Docker 网络；<br>- `host-loopback`：反代在主机网络上，经 `127.0.0.1` 访问。<br>`.env` 中没有这一行时，按 `docker-network` 处理 | 现有 NPM 用户的 `.env` 无需修改 |
| 2 | host-loopback **只发布 web/api 到 `127.0.0.1`**：<br>- `WEB_HOST_PORT`（默认 13000）、`API_HOST_PORT`（默认 18081），范围 1024–65535，不能相同；<br>- db 不发布端口；<br>- 三个服务仍是独立容器，使用各自的桥接网络，**不使用 `network_mode: host`** | 主机网络上的 OpenResty 只能访问主机地址。绑定回环地址后外网不可达；容器保持网络隔离 |
| 3 | **`compose.prod.yaml` 本身保持 docker-network 结构**（与 rc.2 相同，只把 `PROXY_NETWORK` 的必填检查移到 `lib.sh`）。host-loopback 叠加 `compose.host-loopback.yaml`：<br>- 用 `!override` 去掉 api/web 的 proxy 网络；<br>- 用 `!reset` 删除顶层 proxy 网络；<br>- 发布回环端口。<br>`lib.sh` 的 `dc` 只在 host-loopback 时加这个文件 | 演练发现：rc.2 的 `update.sh` 在拉取新代码前已整体读入内存，只会用 `compose.prod.yaml` 启动新版本。<br>最初的写法把 proxy 网络拆到单独的覆盖文件里，结果从 rc.2 升级后 api/web 不在 NPM 网络中，NPM 返回 502。现在的结构保证旧脚本拉起的新版本仍然正确 |
| 4 | host-loopback 需要 **Docker Compose 2.24.4+**（`!override` / `!reset`）：<br>- `load_env` 在该模式下检查版本；<br>- `precheck` 第 7b 节显示是否满足。<br>docker-network 的最低版本仍为 2.20 | 不提高现有 NPM 用户的要求 |
| 5 | host-loopback 的 **`TRUSTED_PROXY_CIDRS` 只写入 `APP_SUBNET`** | 请求经发布端口进入容器时，来源是 app 网络的网关；Nuxt SSR 也在这个网络中。<br>OpenResty 追加的 `X-Forwarded-For` 由 API 从右向左解析，因此只信任这一个网段，不信任 docker0 或任何主机地址 |
| 6 | **端口冲突检查**（`check_host_ports`，install 与 update 都执行）：<br>- 端口有程序监听，且不是本项目（`com.docker.compose.project=xiaowork-blog`）发布的，就拒绝；<br>- 脚本**从不停止其他服务** | 服务器上有 ERP 等其他服务 |
| 7 | **引导式安装**：<br>- 检测到使用主机网络的 openresty / nginx / caddy / traefik 容器时，建议选择 host-loopback；<br>- 之后询问端口（拒绝已占用的端口）；<br>- 安装结束时按模式给出反代配置提示 | 一条命令完成安装 |
| 8 | **`install` 对已在运行的安装执行一次 `dc up -d --no-deps api web`**：<br>- 用于在两种模式之间切换或修改端口：改 `.env` 后再运行 install 即可生效；<br>- compose 只重建配置有变化的容器；<br>- `.env` 没有改动时，演练确认容器不会重建 | 以前服务正常时 install 直接退出，`.env` 的改动不会生效（演练发现） |
| 9 | 新增 1Panel 文档和反代配置：<br>- `docs/deploy/1Panel-OpenResty部署指南.md`；<br>- `deploy/nginx/openresty-host-loopback.conf`。<br>反代地址末尾不加 `/`，保留 `/api/v1`、`/media` 前缀；`Host` 使用域名，`X-Forwarded-Proto` 使用 `$scheme`，`client_max_body_size 12m` | 已知的配置错误点逐一写明 |
| 10 | **演练脚本支持两种模式**：<br>- `DRILL_MODE=host-loopback`：主机网络上的 nginx 模拟 OpenResty；<br>- `SNAPSHOT_SRC`：用旧版本的源码作为第一个提交，测试升级兼容 | 两种模式和旧版本升级都要在隔离环境中实际验证 |

## 后果

- **剩余风险**：host-loopback 下，本机任何使用主机网络的进程都能连到两个回环端口，并自带 `X-Forwarded-For`。这只影响按 IP 计算的限流，不能绕过认证、CSRF 和权限检查。已写入 1Panel 指南 §7 与运维手册 §12。
- 从 host-loopback **回滚到 rc.2 或更早的代码**：旧代码不认识 `PROXY_MODE`，要求 `PROXY_NETWORK`，因此无法以 host-loopback 运行。所以 host-loopback 用户最早只能回滚到 rc.3。NPM 用户回滚到 rc.2 已在演练中验证。
- 切换反代方式时，需要清空 `TRUSTED_PROXY_CIDRS`，让脚本按新模式重新检测；否则旧模式的可信网段会保留。
- 1Panel 的界面本身没有在演练中操作过；指南以最终生成的 OpenResty 配置和上线检查结果为准。

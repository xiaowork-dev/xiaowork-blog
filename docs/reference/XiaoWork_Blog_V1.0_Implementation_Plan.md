### 1.3 本期不可变的产品决策

1. 博客前台：**左侧个人头像/昵称/简介/少量外链图标，右侧文章**，现代简约；个人栏**没有**分类、统计、导航小组件。
2. 文章：Markdown 源码 + 实时预览；已发布文章公开快照和编辑草稿隔离；管理员**手动发布更新**。
3. 账号：邮箱、密码、邮件验证、密码找回，账号需验证邮箱才能评论。
4. 评论：合法评论及回复**立即公开**，管理员事后隐藏/删除/封禁，**没有审核队列**。
5. 图片：服务器本地持久化存储，草稿私有图片需要鉴权；删除有引用资源受保护。
6. V1.0 不加入 GitHub OAuth、记住我、点赞/收藏/站内通知、多作者、文章定时发布或 AI 写作。
7. 网站必须提供 Docker Compose 部署，阶段性交付记录，接入 GitHub 后每次正式改版自动执行提交/推送工作流（权限不可用时如实报告）。

## 2. 设计冻结与实现边界

### 2.1 系统构成

- **`blog-web`**：Nuxt SSR，前台、认证表单、用户中心、管理后台、Markdown 编辑器；不直接连 PostgreSQL。
- **`blog-api`**：Go / Chi 的单体后端，对外 `/api/v1/*` 和 `/media/{media_id}/file`，完成权限、事务、持久化和文件访问。
- **`blog-db`**：一套 PostgreSQL 实例，迁移、备份、查询；不暴露公网。
- **`Nginx Proxy Manager`**：复用现有反向代理实例，按路径代理，不要求重新安装面板或单独为博客安装 NPM；业务 API、数据库不可直接公开。
- **SMTP**：邮件服务由运行环境注入，测试和生产配置分离。

### 2.2 需统一的设计稿细节

| 发现 | 本计划执行规则 |
|---|---|
| 早期架构稿存在 `/uploads/*` 路径，但新的 API-DD 使用 `/media/{id}/file` | **以后者为接口基线**；不并存两套路径，部署规则随实施更新 |
| 早期架构的 API 示例有 `/api/v1/public/*`，但新版接口目录无此层级 | **以 API-DD 的 66 组方法/路径为准**；不要擅自多嵌套 `public` |
| 生成式视觉图含左侧导航/收藏/“记住我”/GitHub 登录 | **全部排除**；视觉稿只参考色彩、布局和密度 |
| UI 草稿建议“关于页保存立即公开” | 延用 API-DD 已确定的 `PUT /admin/pages/about`，UI 要明确提示与文章发布规则不同 |
| PostgreSQL 24 表与 66 路由目前都只是评审稿 | 作为覆盖检查的**设计基线**；实施阶段允许通过 ADR 纠错，但不能无记录缩减已确认功能 |

## 3. 研发工作包总览

> **顺序执行：P0 → P1 → … → P8**。前一阶段的出口检查不通过，不应把相关未解决问题直接带入下一阶段。可以在一个阶段内部按功能做多个小提交，但每个阶段必须形成可复现的可运行增量；**不要一次性让 Agent 完成整个博客**。

| 阶段 | 名称 | 最低交付 | 必须满足的出口检查 |
|---|---|---|---|
| **P0** | 工程骨架、规范和本地一键环境 | Nuxt/Go 工程骨架、Compose、CI、配置示例、交付模板 | 三容器本地健康启动；无秘密信息；Git 推送可核实 |
| **P1** | DB 迁移、核心基础设施 | 24 表迁移基线、pgx/sqlc 接入、通用响应/日志/鉴权基础 | 空数据库迁移成功；再次迁移幂等；约束和回滚测试 |
| **P2** | 注册、登录与邮件认证闭环 | 注册、验证、登录、Session、CSRF、密码找回、管理员初始化 | 真实请求+测试邮件流程跑通；权限、一次性令牌安全通过 |
| **P3** | 本地媒体与上传闭环 | 图片上传、格式检查、受控文件读取、媒体引用和存储持久化 | 上传和草稿私有权限有效；重建容器文件不丢失 |
| **P4** | 文章编辑及发布引擎 | Markdown 编辑、草稿自动保存、Revision 冲突、发布事务、撤回/恢复 | 改草稿不污染公开内容；并发 409、发布事务、回收站验收 |
| **P5** | 博客公开前台与 SEO | 首页/详情、分类标签、归档、搜索、关于、导航、主题、RSS/Sitemap | SSR 内容正确、旧 Slug 301、私有内容 404、移动布局通过 |
| **P6** | 评论互动与用户中心 | 评论/回复/删除、管理员事后治理、资料修改、我的评论 | 已验证账号评论即公开，受限账号不可发，角色权限正确 |
| **P7** | 完善管理后台和网站设置 | 控制台、用户/评论/媒体管理、导航外链、Logo、SEO 默认项 | 所有 V1.0 后台操作可用，普通用户无法越权 |
| **P8** | 质量、安全、正式部署和发布 | E2E、UAT、备份恢复、生产 Compose/NPM、升级与回滚指南、版本发布 | 14 项 UAT、核心安全用例、恢复演练、GitHub 版本记录通过 |

**关于 P1：** 24 表仅表示迁移目标的完整覆盖；可把迁移拆为若干按领域编号的文件，在此阶段用空库验证，再随着后续实际 API 联调修复；不鼓励把 24 张表硬写在一份不可回滚的 SQL 里。

## 4. 每个阶段具体任务、测试与交付

### P0 — 工程骨架 / 团队协作规范 / 本地环境

**开发任务**

- 建立 Monorepo（建议）`apps/web`（Nuxt 4 + TypeScript）、`apps/api`（Go + Chi）；`deploy/`、`docs/`、`scripts/`；用根目录 `README.md` + `AGENTS.md` 或通用协作规范承载规则。
- 本地安装/检验 Go、Node/pnpm、Docker Compose。创建最小前端页面、Go 健康检查端点、PostgreSQL 容器。
- 实现 `.env.example`、严格 `.gitignore`、健康检查、结构化日志、容器非 root 优先、镜像/依赖版本锁定。不得将数据库密码、SMTP 口令、真实用户文件放仓库。
- Compose 从 P0 就存在；开发环境允许仅绑定 `127.0.0.1` 的端口供调试，生产禁止后端和 DB 裸露公网。不要为了“能访问”开放所有接口端口。
- CI 最低跑 Go 测试/格式检查、Nuxt typecheck/lint/build、容器配置校验；真实工具指令以初始化项目脚本为准。

**阶段通过条件**：从干净目录按 README 可以运行站点占位页与 API health；三个容器健康；代码通过基础检查；提交推送远端成功（如已授权），留下 SHA 及推送结果。

### P1 — 数据库与 Go 公共基础设施

**开发任务**

- 按数据库 DD 建立有序迁移，覆盖 users、sessions/tokens、articles/drafts/publications、taxonomy、comments、media、site、audit 等 24 张表；用 goose 或经确认的迁移方案管理版本。
- pgx 连接池、sqlc 查询生成、事务封装、配置验证、统一错误响应与 request_id、安全日志。
- 实现 API 路由权限分组和内部模块层次；只写基础设施，不需要在此阶段一次性把 66 个接口写完。
- 为 FK、唯一键、软删除、评论树约束、草稿与公开标签/媒体关联建立数据库集成测试。

**阶段通过条件**：新数据库能 `up`；重复执行不破坏数据；按迁移方案验证 `down`/恢复可控；约束测试可复现；Go 测试通过。

### P2 — 完整认证闭环

**开发任务**

- 邮箱/密码注册、邮件验证、重发验证、登录退出、服务端 Session、`HttpOnly`+`Secure` Cookie、CSRF、找回/重置密码；后台管理员安全初始化。
- 在 Nuxt 构建登录、注册、验证确认、忘记密码、重置密码页面；GET 链接**不能自动消费令牌**，须用户确认后 POST。
- 邮件错误可解释但避免账号枚举；Session 撤销、被禁用账号拒绝继续认证；敏感接口限流。

**阶段通过条件**：注册→收邮件→验证→登录→登出；重置密码一次性、过期与重复消费；受保护 API 对游客和普通用户返回正确状态；CSRF 和会话过期测试通过。

### P3 — 本地图片/媒体与权限

**开发任务**

- 上传 JPG/PNG/WebP/GIF，验证扩展名/实际 MIME/图片解码/上限、随机命名及尺寸/元数据；文件放 Docker 外持久化目录。
- 提供后台媒体库基本上传、预览、选择、复制引用、删除；用户头像走单独有权限的入口。
- 文章草稿媒体是受保护资源；只有正式发布并且确实有公开引用，才能匿名访问相应图片。通过 `/media/{id}/file` 鉴权读取。
- 删除文件检查文章、个人头像、关于页及站点配置等引用；建立文件/数据库补偿与清理策略。

**阶段通过条件**：伪装格式拒绝、超限可解释；已登录管理员可见私图而游客 404；已引用文件不可删除；容器重建后文件仍在。

### P4 — 文章编辑、草稿和发布

**开发任务**

- 后端：创建文章、读取草稿、`PUT /admin/articles/{id}/draft` 全量覆盖、`expected_revision` 比较并交换、发布/撤回/回收/恢复；公开快照包括标题/Slug/标签/封面/SEO/评论开关。
- 前端：宽屏 Markdown 原文/分栏/预览，草稿自动保存状态、导入/导出 `.md`、文章元信息设置抽屉、发布前确认与“查看已发布文章”链接。
- 发布必须在 DB 事务中原子处理；发布前旧公开内容维持不变；同一修订重复发布幂等，失联时核查服务端状态再重试。

**阶段通过条件**：草稿内容自动保存而公开页面不变；二端同时保存引发 `409 DRAFT_REVISION_CONFLICT` 时本地原文不丢；手动发布后公开内容一致；撤回与恢复不会误发布。

### P5 — 公开博客和内容发现

**开发任务**

- Nuxt SSR 公开页面：`/`、`/posts/:slug`、分类/标签/归档、搜索、关于页；左简洁个人栏 + 右文章内容、PC Sticky、手机单栏。
- 编辑后的文章卡片、阅读目录、Markdown 安全渲染/代码复制、图片放大；亮色/深色/跟随系统；文章分页、空态、错误态。
- SEO：真实 SSR title/meta/canonical/OG、RSS/Sitemap/robots、旧 Slug 301；草稿/撤回/删除不进入搜索/公开页面。
- 中文搜索用真实文章样例验收，不以英文全文检索表现替代中文测试。

**阶段通过条件**：SEO 页面服务端完整返回且 HTTP 状态正确；桌面和移动主要视口检查通过；公开页面无私有数据；旧 Slug 301 仅针对仍公开文章。

### P6 — 评论闭环与个人中心

**开发任务**

- 发表评论、回复、分页、显示昵称/头像、最多 2 层视觉缩进，数据库保存真实父级关系；提交合法评论成功后**立即公开**。
- 未登录给登录入口，未验证给验证提示，禁用账号禁止发言，文章关闭评论拒绝新评论；限流、防 XSS，保持评论框失败内容。
- 用户中心：个人资料、头像、邮箱修改验证、修改密码、退出所有设备、我的评论及自行删除；管理员事后隐藏/恢复/删除违规评论。

**阶段通过条件**：评论发布无需审核；用户只能删自己评论；删除有子项保持墓碑；不同账号、游客、管理员的权限测试通过。

### P7 — 后台完成与配置

**开发任务**

- 完成文章、分类、标签、用户、评论、媒体管理；控制台为基础统计和近期动态，不增加复杂分析。
- 站点配置：站名、Logo/Favicon、个人简介、左侧外链图标地址顺序、顶部导航、SEO 默认设置；关于页内容编辑并清晰提示“保存后立即公开”。
- 所有破坏性操作二次确认、结果可追溯、管理员鉴权在 Go 层强制执行。

**阶段通过条件**：后台各入口都有正常、空、错误、权限状态；外链后台修改后前台生效；普通用户不能调用任何 admin API；没有审核队列、第三方登录或收藏等额外功能。

### P8 — 综合测试 / Docker 交付 / 正式上线

**开发任务**

- 运行 Go 单元与 DB 集成测试、API 契约测试、Nuxt 类型和组件测试、关键 E2E，覆盖 PRD 14 项 UAT；对设计中的 30 API、30 UI 检查项形成可追踪清单。失败项要修复或明确记录不能上线。
- 安全审查：SSR 私密状态、CSRF、XSS、会话撤销、账号枚举、评论刷屏、上传权限、私有媒体访问、日志脱敏。
- 升级/备份/恢复演练：空服务器部署、容器重建、PostgreSQL + 图片 + 配置备份恢复、迁移失败应急、异机/异盘副本验证。
- 部署前核对 NPM Docker 网络和 `/api/v1`、`/media` 路径代理，只开放必要入口；验证 HTTPS 与 Cookie 行为。
- 形成 `v1.0.0` 发布记录、数据库迁移版本、部署/升级/恢复/回滚文档、最终验收报告。

**上线门槛**：没有 P0 级安全/数据丢失缺陷；UAT 项经过真实执行；备份恢复至少成功演练一次；网页健康检查、SMTP、评论、草稿发布链路通过；Git 提交/tag/远端推送可验证。

**特别回归用例（必须列入测试）**：

1. 已发布文章修改标题/Slug/封面/正文/标签/评论开关只改变草稿；发布之前所有公开 API/页面必须保持旧值。
2. 两端同时编辑同一文章：旧 `expected_revision` 返回 409，前端文本保留。
3. 网络超时后重复发布同一修订不得导致重复版本、重复审计或时间异常；已撤回后的显式重发除外。
4. 用户将邮箱验证链接或密码重置链接重复使用，必须被拒绝。
5. 公开评论直接展示；没有“待审核”返回状态；游客、未验证和禁用账号无法发表评论。
6. 上传私有草稿图片后，知道媒体 UUID 的游客仍不能取得文件；容器重建后已上传图片存在。
7. 被引用媒体不可直接删除；文章删除/恢复不能意外删除图片和评论关系。
8. 文章撤回/回收后：详情、搜索、Sitemap、RSS、旧 Slug 和评论公开读取均不可泄露内容。

## 6. GitHub、Agent 与阶段交付制度（所有阶段强制）

### 6.1 Git 工作原则

- 建议使用**一个私有仓库**保存 Nuxt + Go + 部署/文档，除非用户明确另选。可采用 `main` + `feature/pN-xxx` 或同等受保护分支流程。
- 每个独立变化产生说明清楚的 commit（如 `feat(auth): ...`、`fix(article): ...`、`docs: ...`）；**每个完成的阶段和正式改版都必须推送 GitHub**，并记录 commit SHA、远端分支及推送结果。
- 不能凭本地 `git commit` 推断远端已更新；必须验证 `git push` 成功并核对远端状态。凭据不足时停止宣称“已同步”，保留本地提交并在交付记录中报告阻塞。
- `.env`、Token、私钥、SMTP 密钥、真实数据库转储、图片上传目录、备份文件、用户隐私数据不得进仓库。发现已误提交密钥，应视为凭据泄露及时轮换，单纯删文件不等于撤销泄漏。
- 数据库迁移、API 接口及 UI 行为变更，必须一并更新相关设计/实现文档与回归测试，不允许只改代码。

### 6.2 每一步的交付文档模板

路径建议 `docs/handoffs/PX_交付记录.md`，最少包含：

1. 阶段编号、目标、对应 PRD/API/UI 条目与实际范围；
2. 已修改文件/模块及实现内容；
3. **真实运行**的检查命令、退出状态、测试数量及结果；没运行则写“未运行”和原因；
4. 手工验证路径/截图（若有），不得伪造；
5. 风险、已知问题、需用户确认的设计偏差与变更记录 ADR；
6. 数据库迁移/环境变量/部署变更及回退注意事项；
7. Git branch、commit SHA、推送结果及版本号；
8. 下一阶段任务与依赖。

**阶段出口（Definition of Done）**：功能实现 + 测试通过或透明列出失败 + 文档更新 + Git 提交推送成功（需要有可用凭据）+ 安全检查完成 + 用户可按说明复现；任一缺失则标记为**未完成/有阻塞**。

### 6.3 面向任何 Agent 的执行规范

- 一次只接收**一个阶段**（例如 P0）的执行指令，并读取完整 PRD/SAD/DD/API/UI/视觉评审备注以及本实施计划。
- 开始前输出本阶段任务与依赖核查；有业务冲突先形成 ADR，不擅自改变功能范围。
- 先实现可运行最小闭环，再完善边界、测试和文档；不要一次性生成所有模块的假接口/假数据并称完成。
- 需要操作真实服务器、推送仓库、修改 DNS 或处理真实 SMTP 凭据时，应以用户当次授权与当前可用权限为准；本计划不授权实际操作。
- 当前测试结果必须来自已执行的命令/请求；设计稿的用例数不等于已经通过的测试数。

## 8. 风险台账与决策门槛

| 风险 | 影响 | 预防/验证 |
|---|---|---|
| 大量表与业务规则一次性生成 | 迁移难维护、约束不完整 | P1 分领域迁移 + 空库/回滚测试；后续随 API 集成持续修正 |
| SSR 缓存泄漏登录态/草稿 | 私人数据泄露 | Nuxt 与 Go 端 SSR headers/缓存测试；私有响应 no-store |
| Cookie、Session 与跨层 CSRF 处理不一致 | 登录失败或安全漏洞 | P2 固定单域代理、HttpOnly Session、CSRF Token/Origin 联合测试 |
| 文章并发保存与图片引用同步不一致 | 数据丢失、线上图片失效 | Revision CAS + 发布 DB 事务 + 文件引用清理集成测试 |
| 中文全文搜索召回不佳 | 搜索不好用 | P5 用中文词组/短关键词样本验收并按结果调整实现 |
| 本地媒体只有同机备份 | 整机故障丢失 | 上线前完成异机/异盘备份和恢复演练 |
| SMTP 服务不稳定 | 注册/找回流程不可用 | P2 测试邮件服务与正式 SMTP 分离，失败重试/错误处理 |
| 视觉概念图与真实功能不完全一致 | Agent 误开发非 V1 功能 | 视觉评审排除项 + PRD/API 优先级 + UI 回归检查 |
| GitHub 凭据或网络无法推送 | 版本无法同步 | 每阶段验证远端 commit，失败明确写出阻塞及补救动作 |

**无需现在最终确定的项**：真实头像/文案、域名、SMTP 实际密钥、服务器磁盘路径、NPM 网络名称、仓库 URL。这些在 P0/P2/P8 对应阶段通过受控配置补齐，不能把占位值写成真实凭据。

## 9. 开工、暂停与发布决策点

**G0 — 开发授权：** 用户明确说“开始开发 P0”或等效指令，才创建仓库/代码/环境。  
**G1 — P0 出口：** 本地三服务可启动，基础 CI、Git 和交付模板就绪。  
**G2 — 核心业务：** P2 注册闭环、P4 草稿/发布及 P6 评论闭环测试通过。  
**G3 — 视觉和功能：** P5/P7 与 UI 设计、PRD 一致，没有偷加排除功能。  
**G4 — 上线：** P8 14 项 UAT、安全校验、真实恢复演练、可用域名/HTTPS，形成 `v1.0.0` 发布记录。

原则：**设计批准不等于生产发布批准**；可先在本地/测试环境逐步运行。上线操作需明确核对环境、备份和凭据。

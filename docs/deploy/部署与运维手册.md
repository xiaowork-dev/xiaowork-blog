## 1. 架构与前提

```
浏览器 ──HTTPS──► Nginx Proxy Manager（已有的独立服务，占用 80/443）
                    │  共享 Docker 网络 PROXY_NETWORK
                    ├─ /api/v1/*、/media/* ──► xiaowork-blog-api:8080（Go）
                    └─ 其他路径           ──► xiaowork-blog-web:3000（Nuxt SSR）
                                               │ app 网络（固定网段 APP_SUBNET）
                                               ▼
                                         api ──backend 网络（internal，无外网）──► db（PostgreSQL 18）
```

上图是默认的 `PROXY_MODE=docker-network`：反代是一个容器，与 web/api 共享 Docker 网络，本项目的容器**不发布任何主机端口**。

反代使用主机网络时（例如 1Panel 的 OpenResty），使用 `PROXY_MODE=host-loopback`：

```
浏览器 ──HTTPS──► OpenResty / nginx（主机网络，占用 80/443）
                    ├─ /api/v1/*、/media/* ──► 127.0.0.1:API_HOST_PORT（默认 18081）──► api 容器 :8080
                    └─ 其他路径           ──► 127.0.0.1:WEB_HOST_PORT（默认 13000）──► web 容器 :3000
```

- 两种方式下 db / api / web 都是独立容器，使用各自的桥接网络，不使用主机网络。
- host-loopback 只把 web/api 发布到 `127.0.0.1`，外网不可达。
- 数据库在两种方式下都只在内部网络上，不发布端口。
- compose 文件：
  - `deploy/compose.prod.yaml` 本身就是 docker-network 模式；
  - host-loopback 模式会再叠加 `deploy/compose.host-loopback.yaml`，由 `lib.sh` 的 `dc` 按 `PROXY_MODE` 自动选择。
- 1Panel 的完整步骤见 `docs/deploy/1Panel-OpenResty部署指南.md`。
- 持久化数据：
  - 数据库在命名卷 `xiaowork-blog_pgdata`；
  - 图片在主机目录 `DATA_DIR/media`；
  - 备份在 `DATA_DIR/backups`；
  - 版本状态在 `DATA_DIR/state`。
- 镜像在服务器上用当前 Git 提交构建，标签为 12 位提交 SHA；保留当前与上一版本用于回滚。
- 所有脚本位于 `deploy/`，需用 root 或 docker 组用户运行，并且都可以重复执行。

## 2. 服务器准备

| 项目 | 要求 |
|---|---|
| 系统 | 64 位 Linux（演练使用 Alpine 3.22 + Docker 29.8；Debian/Ubuntu 同样适用） |
| Docker | Docker Engine 24+，Compose 插件 **2.20+**（`docker compose version`）；host-loopback 需要 **2.24.4+** |
| 工具 | `git`、`openssl`、`sha256sum`（coreutils）、`bash` |
| 资源 | 建议 2 vCPU / 2 GB 内存以上；构建镜像时需要更多内存。演练中运行时内存约为 api 11 MB、web 210 MB、db 130 MB |
| 磁盘 | `DATA_DIR` 所在分区至少剩余 3 GB（`install.sh` / `update.sh` 会检查），另需为备份预留空间 |
| 网络 | 能访问 GitHub、Docker Hub、Go 模块代理与 npm 源；国内网络可在 `.env` 中设置 `GOPROXY` / `NPM_REGISTRY` 镜像 |
| 反向代理 | docker-network：已运行的 Nginx Proxy Manager，以及它所在的 Docker 网络名（`docker network ls`，常见为 `npm_default`）；host-loopback：主机网络上的 OpenResty / nginx（如 1Panel），以及两个空闲的本机端口（默认 13000、18081） |
| 域名 | DNS A/AAAA 记录指向服务器 |

## 3. 首次安装

```bash
sudo git clone https://github.com/xiaowork-dev/xiaowork-blog.git /opt/xiaowork-blog
cd /opt/xiaowork-blog
sudo deploy/manage.sh precheck      # 可选：只读环境预检（§2、§13），不做任何修改
sudo deploy/manage.sh install
```

`manage.sh install` 的执行过程：

1. 从 GitHub Releases 取得最新的**正式版本**（不会选预发布版本、草稿或 `main` 上未发布的提交），显示版本号与发布日期；输入版本号确认后，代码切换到该版本的标签。
   - 指定版本：`install v1.0.1`。
   - 包含预发布版本：`--pre`。
   - 安装未发布的开发代码只用于测试，必须写成 `install --allow-unreleased main`。
2. 第一次运行时，`install.sh` 生成 `deploy/.env`，数据库密码与 `APP_SECRET_KEY` 随机生成，只保存在本机。在终端中运行时，会接着逐项询问：
   - 域名；
   - 数据目录；
   - 反代方式：
     - 检测到使用主机网络的 OpenResty / nginx / Caddy / Traefik 容器时，建议 `host-loopback`；
     - 否则默认 `docker-network`；
   - docker-network：NPM 所在的网络（列出现有自定义网络及其中的容器）；host-loopback：web 与 api 的本机端口（检查是否被占用、两者不能相同）；
   - 内部网段（自动推荐一个不与现有网络重叠的网段）；
   - SMTP 主机、端口、TLS、用户名、密码（输入时不显示）、发件人。

   输入的值写入 `.env` 时加单引号，避免 `$`、`#` 等字符被误解析。不在终端中运行时，只生成文件并退出，请手动编辑后再运行一次。
3. 安装前检查（发现问题时停止，**不会停止或修改任何其他服务**）：
   - 内部网段是否与现有 Docker 网络重叠；
   - docker-network：NPM 网络是否为自定义网络；
   - host-loopback：两个本机端口是否被其他程序占用；
   - 443 端口是否有程序在监听；
   - 磁盘空间。
4. 构建 → 迁移 → 启动 → 健康检查 → 冒烟测试。

不在终端中运行（例如自动化工具）时，必须加 `--yes`，否则不会执行。本项目**不提供** `curl … | bash` 形式的安装。

`deploy/.env` 的内容（模板为 `deploy/env.production.example`；文件权限 600，已被 Git 忽略，**不得提交**）：

| 变量 | 说明 |
|---|---|
| `PUBLIC_BASE_URL` | 正式地址，必须是 `https://`，不含路径，例如 `https://blog.example.com` |
| `DATA_DIR` | 持久化目录的绝对路径，不能放在代码目录内，默认 `/srv/xiaowork-blog` |
| `POSTGRES_PASSWORD`、`APP_SECRET_KEY` | 第一次运行时自动随机生成，**之后不要修改**：改密码会导致无法连接已有数据库，改密钥会使现有 CSRF 令牌失效 |
| `SMTP_*` | 发信服务。公网站点只允许 `starttls`（587）或 `tls`（465）；`SMTP_PASSWORD` 只写在服务器上 |
| `PROXY_MODE` | `docker-network`（默认；旧的 `.env` 没有这一行时也按它处理）或 `host-loopback` |
| `PROXY_NETWORK` | docker-network：NPM 所在的 Docker 网络名，必须已存在；host-loopback 不使用 |
| `WEB_HOST_PORT`、`API_HOST_PORT` | host-loopback：web / api 发布到 `127.0.0.1` 的端口，默认 13000 / 18081，范围 1024–65535 |
| `APP_SUBNET` | 本项目内部 app 网络的网段，与其他网络冲突时才需要修改 |
| `TRUSTED_PROXY_CIDRS` | 留空，由脚本自动检测（见 §12） |
| `BACKUP_KEEP` | 保留的备份份数，默认 14 |
| `GOPROXY`、`NPM_REGISTRY` | 可选的构建镜像源 |

文件按 Docker Compose 的 dotenv 语法逐行读取（`KEY=value`，不支持行尾注释）。值中含有 `$`、`#`、空格或引号时，用单引号括起来（`KEY='va$lue'`），值本身不能包含单引号。仍为 `CHANGE_ME` 的值会被脚本拒绝。

安装成功后会输出版本号与数据库结构版本。再次运行 `manage.sh install` 时，如果服务正常，只按 `deploy/.env` 的改动重新创建有变化的容器（例如切换 `PROXY_MODE` 或修改端口；没有改动时不重建任何容器），然后退出；如果服务异常，会重新启动已记录的版本，**不切换版本，不删除任何数据**。

## 4. 配置反向代理（NPM / 1Panel）

**host-loopback（1Panel OpenResty 等）**：

- 按 `docs/deploy/1Panel-OpenResty部署指南.md` 配置：`/` → `http://127.0.0.1:13000`，`/api/v1/` 与 `/media/` → `http://127.0.0.1:18081`；
- 代理地址末尾不加 `/`，以保留路径前缀；
- 等价的 nginx 配置为 `deploy/nginx/openresty-host-loopback.conf`；
- 切换反代方式的步骤见该指南第 8 节。

下面是默认的 **docker-network（Nginx Proxy Manager）**。在 NPM 中新建 **Proxy Host**：

| 位置 | 设置 |
|---|---|
| Details | Domain Names：正式域名；Scheme `http`；Forward Hostname `xiaowork-blog-web`；Port `3000`；勾选 **Block Common Exploits**；不需要 Websockets Support |
| Custom locations | 新增两条，都指向 Scheme `http`、Forward Hostname `xiaowork-blog-api`、Port `8080`：<br>Location `/api/v1/`<br>Location `/media/` |
| SSL | 申请 Let's Encrypt 证书；勾选 **Force SSL**、**HTTP/2 Support**；HSTS 可以开启（应用本身也会发送一年的 HSTS） |
| Advanced | `client_max_body_size 12m;`（图片上传上限为 10 MiB，加上 multipart 开销） |

说明：

- 主机名 `xiaowork-blog-web` 与 `xiaowork-blog-api` 是 `compose.prod.yaml` 在 `PROXY_NETWORK` 上设置的网络别名，NPM 容器必须在同一网络中。该网络必须是**自定义网络**：Docker 预置的 `bridge` 没有容器名解析，脚本会拒绝 `bridge` / `host` / `none`。NPM 只在默认 bridge 上时，见 `docs/handoffs/P8-B1_部署预检准备.md` §5.2 方案 B。
- 部署前可用只读脚本 `deploy/precheck.sh` 检查服务器（不做任何修改），用法见该文档 §4。
- NPM 默认会传递 `Host`、`X-Forwarded-For`、`X-Forwarded-Proto` 和 `X-Real-IP`，无需额外配置。
- 不要在 NPM 中为本站开启缓存。后台、个人中心与认证页面都带有 `Cache-Control: private, no-store`。
- 等价的纯 nginx 配置见 `deploy/nginx/npm-equivalent.conf`，演练环境使用的就是这份配置。

**检查（在服务器上执行）：**

```bash
curl -sI https://你的域名/ | grep -iE 'HTTP/|strict-transport|content-security'
curl -s https://你的域名/robots.txt
curl -s https://你的域名/api/v1/site
```

**确认真实客户端 IP**：用手机网络访问一次站点，然后执行：

```bash
docker logs --tail 5 <NPM 容器名>
```

日志中的客户端地址应是公网 IP。如果所有请求都显示为 Docker 网关地址（如 `172.x.0.1`），说明 NPM 拿不到真实 IP（常见于 rootless Docker 或关闭了 iptables），此时限流只能按网关 IP 生效。这需要先在 NPM 一侧解决，或者把所有用户共用一个 IP 当作已知风险接受。

## 5. 初始化管理员

后台**没有**创建管理员或提升角色的功能（ADR-0007）。第一个管理员只能在服务器上创建：

```bash
sudo deploy/manage.sh admin create-admin -email you@example.com -nickname 博主
```

脚本会提示输入两次密码（12–128 个字符），输入时不回显，密码不会出现在命令行、进程列表或日志中。非交互执行时，可以从权限为 600 的文件中读取第一行：`sudo deploy/manage.sh admin create-admin -email … -nickname … < /root/admin-pw.txt`（用完即删）。已经存在管理员时，该命令会拒绝执行。创建后在 `https://你的域名/auth/login` 登录，进入 **网站设置** 修改站名、简介、头像等。

## 6. 日常运维

| 操作 | 命令 |
|---|---|
| 菜单 | `sudo deploy/manage.sh` |
| 状态（正式版本号、提交、结构版本、健康、最近记录） | `sudo deploy/manage.sh status` |
| 日志 | `sudo docker compose -p xiaowork-blog logs --tail 100 api web` |
| 媒体一致性检查 | `sudo deploy/manage.sh admin media-check` |
| 立即备份 | `sudo deploy/manage.sh backup --label manual` |
| 只读环境预检 | `sudo deploy/manage.sh precheck`（自动带上 `.env` 中的网络、域名、SMTP 参数） |
| 定时备份 | `sudo crontab -e`，添加 `30 3 * * * /opt/xiaowork-blog/deploy/manage.sh backup --label daily >> /srv/xiaowork-blog/backups/backup.log 2>&1` |

- 日志使用 json-file 驱动，每个容器最多 5 × 10 MB。API 日志不记录密码、令牌或 Cookie。数据库使用 `log_error_verbosity=terse`，不会把约束冲突中的邮箱写入日志。
- **任何时候都不要执行** `docker compose down -v`、`docker volume rm xiaowork-blog_pgdata`，也不要用 `rm -rf` 删除 `DATA_DIR`。

## 7. 版本更新

```bash
sudo deploy/manage.sh check            # 查看 GitHub 上的正式版本以及是否有更新（加 --pre 显示预发布版本）
sudo deploy/manage.sh update           # 更新到最新正式版
sudo deploy/manage.sh update v1.0.1    # 更新（或降级）到指定的已发布版本
```

**版本来源与类型**：

- 版本列表来自 GitHub Releases（`https://api.github.com`，匿名访问即可；可以设置 `GITHUB_TOKEN` 提高速率限制）。只有标签形如 `vX.Y.Z` 的已发布 Release 才算版本，草稿会被忽略。
- **正式版**：默认推荐的版本。
- **预发布版**：标签带 `-rc.1` 之类的后缀，或在 GitHub 上标为 pre-release。只有加 `--pre` 才会显示和选用。
- **开发代码**：`main` 分支上未发布的提交只作为信息显示，不会被当作更新；确实需要时必须写 `update --allow-unreleased main`，不建议用于生产。

**更新前显示的计划**：

- 当前版本与目标版本（版本号、提交、发布日期）；
- 方向：升级、降级，或切换到另一条提交线；
- 将要执行的数据库迁移；降级时列出目标版本不认识的已执行迁移；
- 更新说明的前 25 行。

需要输入目标版本号确认。不在终端中运行时必须加 `--yes`，否则拒绝执行。

**安全检查**：

- 无法访问 GitHub、API 返回错误（如速率限制）、响应格式不对、版本不存在时，命令报错退出，**网站不受影响**。
- 服务器记录了每个已部署标签对应的提交（`DATA_DIR/state/tags`）。如果远端的同名标签被移动，命令拒绝继续。
- 没有任何定时自动更新，也不会因为 `main` 有新提交而自动部署。

确认后由 `deploy/update.sh --ref <版本>` 执行更新，步骤如下：

1. 检查工具与配置；代码目录有未提交的修改时拒绝更新。
2. 拉取代码并切换到目标版本；已是该版本且运行正常时直接退出。
3. **构建新镜像**，此时网站仍由旧版本提供服务。
4. **完整备份**到 `DATA_DIR/backups/<时间>-pre-update-<版本>`。
5. 应用 db 服务定义的变化（只有配置改变时才会重建容器，数据保留在卷中）。
6. 用新镜像执行数据库迁移。**迁移失败时不切换**，网站继续运行旧版本，代码目录切回旧提交。
7. 切换 api / web 到新镜像，执行健康检查与冒烟测试。
8. 成功后记录版本并清理更早的镜像（保留当前与上一版本）。
9. 新版本没有通过检查时，**自动切回旧镜像**，并提示更新前的备份位置。

更新期间 api / web 重启会有数秒中断，数据库不停机。

## 8. 回滚

```bash
sudo deploy/manage.sh rollback          # 显示当前与上一版本，输入 rollback 确认
```

- 切换到上一版本的镜像（`DATA_DIR/state/previous`），检查健康，并把代码目录切到该提交。再次运行可以切回来。
- **数据库结构不会回退**。迁移遵循“只增不删”，旧代码可以在新结构上运行（演练中，结构版本 8 上运行版本 7 的代码正常）。
- 如果必须让数据回到更新前的状态，使用更新前的备份恢复（§9），**更新后产生的新数据会丢失**：

```bash
sudo deploy/manage.sh restore /srv/xiaowork-blog/backups/<时间>-pre-update-<版本>
```

## 9. 备份与恢复

**备份内容**（`DATA_DIR/backups/<UTC 时间>-<标签>/`）：

| 文件 | 内容 |
|---|---|
| `db.dump` | `pg_dump -Fc` 全库：文章、版本、用户、会话、评论、站点设置、审计日志等 |
| `media.tar.gz` | 全部原图与缩略图 |
| `env.backup` | `deploy/.env` 副本（**含密钥**） |
| `manifest.txt` | 时间、版本、结构版本、图片数量 |
| `SHA256SUMS` | 上述三个文件的校验和 |

备份目录权限为 700，文件权限为 600；超过 `BACKUP_KEEP` 的旧备份会被删除。

**恢复：**

```bash
sudo deploy/manage.sh restore /srv/xiaowork-blog/backups/20261024T033000Z-daily
# 提示时输入 RESTORE 确认；脚本化执行可加 --yes
```

恢复的执行顺序：

1. 校验 SHA256。
2. 先把**当前**状态备份为 `…-before-restore`。
3. 停止 api / web。
4. 重建数据库，再执行 `pg_restore --exit-on-error`。
5. 当前图片目录改名为 `media.before-restore-<时间>` 保留，然后解包备份中的图片。
6. 执行迁移（代码比备份新时）。
7. 启动服务，执行健康检查与冒烟测试。

恢复完成后运行 `deploy/manage.sh admin media-check`，确认无误后再手动删除 `media.before-restore-*`。

> 恢复会让所有用户回到备份时的状态，包括会话：备份之后注册的用户与发表的评论会消失。

## 10. 异地备份

本机备份只能防止误操作，不能防止磁盘或服务器损坏。具体目标存储在 P8-B 确定，以下方案任选其一：

```bash
# 另一台机器（SSH 密钥登录），每天 04:00 同步
0 4 * * * rsync -a --delete-after /srv/xiaowork-blog/backups/ backup@backup-host:/backups/xiaowork-blog/
# 或对象存储（rclone，目标需开启服务端加密或使用 rclone crypt）
0 4 * * * rclone sync /srv/xiaowork-blog/backups remote-crypt:xiaowork-blog
```

- 备份包含 `env.backup`（数据库密码、APP_SECRET_KEY、SMTP 密码）和用户个人数据，目标存储必须私有并加密。
- 至少每季度在另一台机器上按 §11 做一次恢复演练。

## 11. 灾难恢复（换新服务器）

1. 在新服务器上完成 §2（Docker、NPM、网络）。
2. 克隆代码（`git clone … /opt/xiaowork-blog`）。查看备份中的 `manifest.txt`：`app_version` 是备份时运行的提交；在原服务器上用 `deploy/manage.sh status` 记录过的版本号即为对应的发布版本。
3. 把异地备份复制到新服务器，例如 `/root/restore/<备份目录>`。
4. 恢复配置：

   ```bash
   sudo install -m 600 /root/restore/<备份目录>/env.backup deploy/.env
   ```

   - 检查 `DATA_DIR`、`PROXY_NETWORK`；
   - **把 `TRUSTED_PROXY_CIDRS=` 清空**，让脚本重新检测新机器的网络。
5. 运行 `sudo deploy/manage.sh install <备份时的版本号>`（例如 `v1.0.1`；也可以安装更新的正式版本，恢复后会自动执行新增的迁移），安装一个空站点。因为 `deploy/.env` 已经存在，不会再询问配置。
6. 运行 `sudo deploy/manage.sh restore /root/restore/<备份目录> --no-safety-backup`（空站点不需要安全备份）。
7. 按 §4 配置 NPM，把 DNS 指向新服务器。
8. 运行 `sudo deploy/manage.sh admin media-check`，用原管理员账号登录检查。

演练结果：在一台全新的 Linux 环境中按以上步骤恢复后，以下内容与备份前完全一致：

- 文章 30 篇（已发布 13 篇）、用户 8 个、评论 9 条；
- 站点设置、关于页与外链；
- 10 个图片文件的校验和；
- 原管理员密码可以登录。

## 12. 安全要点

- **可信代理**：`TRUSTED_PROXY_CIDRS` 为空时，`install.sh` / `update.sh` 会自动写入：docker-network 写入 `PROXY_NETWORK` 的网段与 `APP_SUBNET`；host-loopback 只写入 `APP_SUBNET`（经 127.0.0.1 发布端口进入的请求来自该网络的网关）。切换反代方式时请清空该值，让脚本重新检测。只有直接对端在这些网段内，API 才会读取 `X-Forwarded-For`。
  - 演练确认：从外部伪造的 `X-Forwarded-For` 被忽略。
  - 剩余风险：docker-network 下，同一 NPM 网络中的其他容器可以伪造来源 IP；host-loopback 下，本机任何使用主机网络的进程都可以连到 127.0.0.1 的两个端口并伪造来源 IP（只影响按 IP 计算的限流，不能绕过登录、CSRF 与权限检查）。
  - 收紧方法：在 NPM 的 compose 中给它固定 IP（如 `ipv4_address: 172.20.0.10`），然后设置 `TRUSTED_PROXY_CIDRS=172.20.0.10/32,172.30.240.0/24`，然后运行 `sudo deploy/update.sh --no-fetch` 让配置生效（不切换版本）。
- **Cookie**：HTTPS 站点使用 `__Host-` 前缀，带 `Secure`、`HttpOnly`（CSRF Cookie 除外）和 `SameSite=Lax`。跨站来源的写请求会返回 403。
- **响应头**：Web 发送 CSP、`X-Frame-Options: DENY`、`nosniff`、`Referrer-Policy`、`Permissions-Policy` 和 HSTS；`/media` 文件带 `Content-Security-Policy: default-src 'none'; sandbox` 与 `nosniff`。
- **图片**：上传时只接受 JPEG / PNG / WebP / GIF，按文件内容判断格式并限制尺寸，并自动移除 EXIF/GPS 等隐私元数据。
- **防火墙**：服务器只需要开放 22、80、443。docker-network 不发布端口；host-loopback 只发布到 127.0.0.1，**不要**在防火墙中放行 13000/18081，也不要改成绑定 `0.0.0.0`。
- **密钥**：`deploy/.env` 与备份目录只有 root 可读，不要把其中任何内容粘贴到工单或聊天中。

## 13. 故障排查

| 现象 | 处理 |
|---|---|
| 安装时提示网络不存在或不能使用 `bridge` | 检查 `PROXY_NETWORK` 与 `docker network ls` 是否一致，且是 NPM 所在的自定义网络 |
| 安装时提示本机端口被占用（host-loopback） | 13000 / 18081 已被其他程序使用。在 `.env` 中换成空闲端口，反代地址同步修改；脚本不会停止占用端口的程序 |
| 提示 host-loopback 需要 Docker Compose 2.24.4 | 升级 compose 插件，或改用 docker-network |
| 1Panel 中首页正常但 `/api/v1/…` 404 | 后端代理地址末尾多了 `/` 或写了路径，见 1Panel 指南 §4.2 |
| 安装时提示 `APP_SUBNET` 与现有网络重叠 | 在 `deploy/.env` 中换一个空闲的 /24 网段（`manage.sh precheck` 第 6 节会列出现有网段） |
| `check` / `update` 提示无法连接 GitHub、HTTP 403 或解析失败 | 网站不受影响。检查服务器能否访问 `api.github.com`；403 通常是匿名速率限制，稍后重试，或设置 `GITHUB_TOKEN`（只需公开仓库的只读权限） |
| `update` 提示标签被移动 | 远端发布标签指向了与之前部署时不同的提交。停止更新，核实仓库来源与发布记录，不要强制处理 |
| 提示“GitHub 上还没有正式发布的版本” | 项目尚未发布正式版本，或你使用的是没有 Release 的分叉仓库。测试时可用 `--allow-unreleased main`，不建议用于生产 |
| 构建时无法下载 Go 模块或 npm 包 | 设置 `GOPROXY=https://goproxy.cn,direct`、`NPM_REGISTRY=https://registry.npmmirror.com/` |
| NPM 显示 502 | 运行 `docker network inspect <PROXY_NETWORK>`，确认 NPM、`xiaowork-blog-web-1` 与 `xiaowork-blog-api-1` 都在其中，再查看 `deploy/manage.sh status` |
| 登录后立即掉线或 403 CSRF | `PUBLIC_BASE_URL` 必须与浏览器地址完全一致（协议、域名、端口）；NPM 必须开启 Force SSL |
| 所有用户共享限流 | 见 §4“确认真实客户端 IP” |
| 收不到验证邮件 | 查看 `docker compose -p xiaowork-blog logs api`，搜索 `mail`；检查 SMTP 端口和 TLS 方式，以及发件域名的 SPF/DKIM |
| 上传图片返回 413 | 在 NPM 的 Advanced 中加上 `client_max_body_size 12m;` |
| 更新失败并自动回滚 | 网站已回到原版本。按脚本输出查看日志，等待修复版本发布后再运行 `manage.sh update`。数据库已迁移时，提示中会给出更新前备份的路径 |
| 更新被中断（SSH 断开） | 运行 `sudo deploy/manage.sh install`，它会重新启动已记录的版本；再执行 `manage.sh update` |

## 14. 隔离演练环境

`deploy/test/drill.sh` 在 Docker-in-Docker 容器中模拟一台全新的 Linux 服务器：

- 默认用 nginx 按 `deploy/nginx/npm-equivalent.conf` 模拟 NPM，并提供自签名 HTTPS；
- `DRILL_MODE=host-loopback` 时，改用主机网络上的 nginx，按 `deploy/nginx/openresty-host-loopback.conf` 模拟 1Panel OpenResty；
- Mailpit 模拟 SMTP；
- 一个裸 Git 仓库扮演 GitHub。

用法见 `deploy/test/README.md`。它不会连接任何生产服务器，也不使用开发机上的 Docker 卷。
